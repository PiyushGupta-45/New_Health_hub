HEALTHHUB PROJECT DOCUMENTATION
Text documentation for the complete project

============================================================
1. PROJECT PURPOSE
============================================================

This repository contains a Flutter application called HealthHub plus a Node.js backend.

At a high level, the project tries to be an all-in-one health and fitness app with these major capabilities:

- user authentication
- daily step tracking
- Health Connect integration
- manual workout logging
- AI workout planning
- AI diet planning
- meal tracking
- habit tracking
- posture analysis using camera and pose detection
- walking missions using geolocation
- communities and chat
- step challenges and mini games
- progress dashboard and streak/reward logic
- Android in-app APK update flow based on GitHub releases

The codebase is split into two main parts:

- Flutter frontend in `lib/`
- Express + MongoDB backend in `backend/`

There are also Android, iOS, web, Linux, macOS, and Windows folders created by Flutter. Most of those platform folders are project scaffolding and runtime configuration rather than business logic.


============================================================
2. HIGH LEVEL ARCHITECTURE
============================================================

The app architecture is a pragmatic feature-based Flutter structure, not a heavy layered architecture.

Main building blocks:

- `pages/` contains UI screens and major feature views.
- `services/` contains data access, API wrappers, local storage helpers, AI helpers, update logic, step logic, and workout logic.
- `controllers/` contains app-level state coordinators for auth and health sync.
- `models/` contains reusable data models and enums.
- `widgets/` contains reusable UI widgets.
- `painters/` contains custom drawing helpers.
- native Android Kotlin code handles low-level step sensor access and update/install helper methods.
- `backend/server.js` provides REST APIs and MongoDB persistence.

Typical data flow:

1. A page asks a controller or service for data.
2. Controllers coordinate multiple services and expose UI-friendly state.
3. Services either call backend APIs, read local `SharedPreferences`, call native Android through `MethodChannel`, call Hugging Face text generation, or process local device health and sensor data.
4. UI rebuilds using the latest state.


============================================================
3. APP STARTUP FLOW
============================================================

Startup order:

1. `lib/main.dart` starts Flutter, attempts to load `.env`, and launches `MyApp`.
2. `MyApp` creates a `ThemeService` provider and builds the main `MaterialApp`.
3. Home screen of the app is `SplashScreen`.
4. `lib/pages/splash_screen.dart` shows a branded splash for 2 seconds.
5. After the timer finishes, it pushes `MainScreen`.
6. `lib/main_screen.dart` becomes the real app shell.
7. `MainScreen` creates `AuthController`, `HealthSyncController`, and `AppUpdateService`.
8. `MainScreen` decides whether to show the auth flow or the main tabbed application.
9. After first render, `MainScreen` also checks for Android app updates.

Main tabs managed by `MainScreen`:

- Home
- Community
- Features
- Dashboard


============================================================
4. IMPORTANT DIFFICULT CONCEPTS
============================================================

4.1 Authentication model

Authentication is handled by Flutter `AuthService` and `AuthController`, backend `/api/auth/*` routes in `backend/server.js`, and local persistence through `SharedPreferences`.

Important detail:

- The app supports full sign-in and guest mode.
- On the first launch after install or reinstall, `AuthController` deliberately clears stored user data and some step baseline data so the app does not accidentally reuse stale state.
- Session validation is intentionally done in the background after the UI becomes usable. This means startup can still work offline using the last locally stored session.

4.2 Step counting model

This is one of the most complex parts of the codebase.

There are multiple step sources:

- direct Android step sensor through native Kotlin
- Health Connect through the `health` package
- backend cloud-stored daily steps

Why this is hard:

- Android hardware step sensors usually report cumulative steps since boot, not "today's steps".
- The app therefore needs a baseline to compute daily steps.
- Devices behave differently when the app is killed, when sensors batch events, or when permissions are missing.
- The app also wants the displayed value, backend value, and background tracked value to stay consistent.

How the app solves it:

- `DirectStepService` talks to native Kotlin via `MethodChannel`.
- Native Android also runs `StepCounterService` as a foreground service to keep step tracking alive in the background.
- The service stores "today's steps" in native shared preferences.
- Flutter keeps its own baseline data too.
- `HealthSyncController` merges sensor data, cached values, backend sync, and Health Connect sync into one UI snapshot.

4.3 Auto-download and install update model

The app does not use Play Store in-app updates. Instead it uses GitHub releases plus direct APK installation.

The flow is:

1. `MainScreen` calls `_checkForUpdates()` after the first frame.
2. `AppUpdateService.checkForUpdate()` reads `GITHUB_REPO` from `.env`.
3. It calls `https://api.github.com/repos/<owner>/<repo>/releases/latest`.
4. It reads the latest release tag and compares it against the installed app version and build using `PackageInfo`.
5. It looks through the release assets and picks the `.apk` file.
6. If a newer APK exists, `MainScreen` shows an update dialog.
7. Before installation, the app checks whether Android allows this app to install unknown APKs.
8. If not allowed, `MainActivity` opens the system settings page for "Install unknown apps".
9. If allowed, `AppUpdateService.startUpdate()` calls the `ota_update` plugin and downloads the APK into internal storage.
10. The downloaded APK is handed to Android installer UI.
11. The app stores a `pending_update_tag` in `SharedPreferences` so it knows an update is already downloaded or in progress.
12. On a later app start, if the installed version is now at least that tag, the app removes the pending state and deletes leftover APK files.

4.4 Local-first plus backend-sync design

Many features save locally first and sync later or additionally.

Examples:

- auth session is stored locally
- goals are stored locally
- habits are stored locally
- posture history is stored locally
- recovery check-ins are stored locally
- meal logs are stored locally
- walking missions history is stored locally
- some workout plan data is stored locally and also sent to backend
- steps are synced to backend on intervals

6. HOW THE AUTO DOWNLOAD AND INSTALL SYSTEM WORKS
============================================================

This section explains the updater in more depth because it is one of the most special parts of this project.

Step 1. Trigger

- `MainScreen.initState()` schedules `_checkForUpdates()` after the first frame.
- This means the app UI loads first, then update logic runs.
- Update failure does not block startup.

Step 2. Pending update recovery

- `MainScreen` reads `pending_update_tag` from `SharedPreferences`.
- If it exists, the app asks `AppUpdateService.isInstalledVersionAtLeast(tag)`.
- If the currently installed version is already equal or newer, the app removes the pending tag and calls `cleanupDownloadedApks()`.
- This is post-install cleanup logic.

Step 3. Release discovery

- `AppUpdateService.checkForUpdate()` reads `GITHUB_REPO`.
- Expected format is `owner/repository`.
- It calls GitHub latest release API and parses the JSON response.

Step 4. Version comparison

- Local version comes from `PackageInfo`.
- Remote version comes from GitHub `tag_name`.
- `_normalizeVersion()` strips prefixes like `v`, replaces separators, and compares version segments numerically.
- If the remote version is not newer, the flow ends quietly.

Step 5. APK asset selection

- The service searches release assets for a URL ending in `.apk`.
- If the release has no APK, update flow stops.

Step 6. User prompt

- `MainScreen` shows an "Update Available" dialog.
- Release title, version tag, and notes are shown.
- The user can choose to update now or later.

Step 7. Android unknown-source permission

- Before installation, the app calls `canRequestPackageInstalls()` via native `MethodChannel`.
- On Android 8 and above, this checks whether this app can request package installs.
- If false, `MainActivity` opens the system settings screen for "Install unknown apps".

Step 8. Download and installer handoff

- `AppUpdateService.startUpdate()` calls `OtaUpdate().execute(...)`.
- It creates a safe file name like `healthhub_update_<tag>.apk`.
- The `ota_update` plugin downloads the APK into app internal storage.
- Android installer UI is then opened for the downloaded APK.

Step 9. Progress state

- `MainScreen` listens to the `OtaEvent` stream.
- It updates UI labels for states such as downloading, installing, or failure.
- It stores `pending_update_tag` while download is happening.

Step 10. Native file exposure and cleanup

- `AndroidManifest.xml` registers `sk.fourq.otaupdate.OtaUpdateFileProvider`.
- `filepaths.xml` grants safe access to files under the internal OTA folder.
- `MainActivity.cleanupDownloadedApks()` deletes leftover APK files from:
  - `filesDir/ota_update`
  - legacy APK files in `filesDir`

Why cleanup matters:

- prevents storage waste
- avoids stale APK confusion
- avoids repeated install of an old file

Design strengths:

- simple release pipeline
- no Play Store dependency
- recoverable state through `pending_update_tag`
- user-visible progress

Design tradeoffs:

- effectively Android-only
- requires "install unknown apps" permission
- depends on GitHub release hygiene
- depends on a valid `.apk` asset being attached to the release

7. HOW STEP TRACKING AND BACKGROUND COUNTING WORK
============================================================

This is the other subsystem that deserves deeper explanation.

7.1 Native sensor layer

- `MainActivity` registers listeners for:
  - `TYPE_STEP_COUNTER`
  - `TYPE_STEP_DETECTOR`
- `TYPE_STEP_COUNTER` gives cumulative steps since boot.
- `TYPE_STEP_DETECTOR` gives one callback per step.

7.2 Foreground service layer

- `StepCounterService` runs as a foreground service.
- It continues listening even outside the Flutter page lifecycle.
- It stores values in Android shared preferences.

Important stored values:

- last cumulative count
- current day key
- day start cumulative count
- today's step total

7.3 Boot and restart recovery

- `StepBootReceiver` restarts the service on:
  - device boot
  - app package replacement
  - quick boot
  - explicit restart broadcast

- `StepCounterService` also tries to restart itself if the task is removed.

7.4 Flutter bridge layer

- `DirectStepService` calls native methods with `MethodChannel`.
- Flutter can ask for:
  - current count
  - today's steps
  - start listening
  - battery settings state
  - auto-start settings

7.5 Controller merge layer

- `HealthSyncController` merges:
  - direct sensor data
  - native today-step data
  - local baseline logic
  - backend sync
  - Health Connect data

Why this merge exists:

- some devices delay cumulative events
- some devices keep native daily count correct even if callbacks are stale
- backend may already have a higher confirmed value
- UI should not jump backward

7.6 Backend sync layer

- `HealthSyncController` periodically sends current step totals to backend through `StepsSyncService`.
- It also hydrates from backend so the app can recover state after restart or reinstall.

Net effect:

- The app tries to be resilient against Android sensor quirks, app restarts, and inconsistent event timing.

10. FINAL SUMMARY
============================================================

HealthHub is a multi-feature Flutter health platform with a Node backend.

The app is built around four especially important systems:

- auth and account management
- step tracking and sync
- workout, goals, and AI planning
- community and challenge engagement

The two most technically special parts are:

- background Android step tracking with native services
- APK auto-update from GitHub releases with direct installer handoff
